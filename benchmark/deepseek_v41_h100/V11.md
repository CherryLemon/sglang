# H100 PD optimization: host scheduling, index scoring and decode

v11 improves warmed coding latency and throughput while retaining the v10 model,
weights, two 8-H100 servers, PD topology and 600k-context support. All four changes
were developed independently and tested as one integration. No feature ablation
or pure-TP/pure-DP comparison was performed.

Base: `788175854896568b2927f50b2cd2b9c0b05c5fbf`.
Runtime payload: `e6a4c2fa1ea8db7c2f9742430826a4b68889d950`.
The environment and model revision are pinned in [README.md](README.md).

## Changes

- **P host work:** Unified cache insertion advances an offset through the request
  key rather than copying the remaining token suffix at every cached node.
  Stored leaves retain their original ownership and bigram-boundary rules.
  Bounded prefill graphs use the same bounded metadata width at capture and
  replay; unknown or over-limit sequence lengths remain eager.
- **P index scoring:** Hopper FP8 scoring uses larger position tiles for
  sufficiently large dense and compact candidate shapes. Dot products,
  rounding, score storage and candidate selection are unchanged.
- **D computation:** Seven H100 block32 FP8 projection shapes receive small-M
  configurations. Newly added shared-expert entries retain FP8 WGMMA; larger-M
  defaults are preserved. See [V11_COMPUTE.md](V11_COMPUTE.md).
- **D scheduling:** DSPARK prepares host metadata before graph admission and
  omits two GPU count uploads only when the CUDA graph registry fills those
  buffers itself. Eager and other-device paths retain the uploads. A duplicate
  non-padded-count upload is removed.

These changes do not establish that the unresolved libc frame in the original
profile was cache insertion, or that communication was bandwidth-limited.
Component improvements are not additive endpoint speedup estimates.

## Correctness and benchmark correction

The combined integration suite passed71 tests plus47 subtests. Component checks
include cache storage/lifetime/backup rules, full655360 index widths and memcheck,
changed-input graph replays, GEMM dispatch boundaries and unchanged numerical
tolerances. Independent review of112 paired DSPARK forward metadata paths was
bit-exact.53 production-quantized GEMM groups and2650 fixed-input replays were
deterministic. These checks do not imply arbitrary whole-model logit equivalence
across batch padding or universal task accuracy.

The final deployment passed single/16-request functionality, serial/concurrent
mixed boundaries, conversations/tools/cancellation, uneven DP activity and two
coding tasks with16 assertions.31 additional known-answer requests cover17
actual tail boundaries, warm45,65536/65537 context admission and32k→600k→32k
switching. Actual graph/eager decisions were correlated with raw query counts,
pending counts, page budgets and all-rank capture logs, with no ambiguous
attribution. Bucket identity is inferred from verified capture sizes and the
smallest-fitting-bucket rule; logs expose graph eligibility directly.

All252 natural-coding requests per arm, including warmups, ended normally.
Every distinct module (23 v10,25 v11) passed514 independent assertions covering
exhaustive small schedules, tie rules, generators, negative weights, validation
and frozen dataclasses. Implementations vary; this is semantic validation, not
claimed token identity. Final runtime hashes matched25 files on both nodes;
services remained healthy and logs contained no ERROR or traceback.

The historical fixed512 workload sets `ignore_eos=true`. Its original c1 code
answer ends at token51 including EOS. Forty native diagnostic responses across
complete v10/v11 versions agree exactly through that EOS; disagreements start
after it. The initial integration showed a14.2% c1 stress-throughput regression;
a fresh complete v10 restart also changed its c1 result from249.6 to204.9tok/s
and reproduced the forced-continuation drift. All results remain in the report.
They cannot alone establish a natural-coding regression or improvement. The
normal-EOS workload above was added to resolve that measurement problem.

Burst1/4/16 results do not establish sustained-arrival SLA capacity,16 simultaneous
600k requests, or accuracy on a broad coding suite. The tested capacity values
are retained; the workload and graph bounds are explicit.
