# H100 block32 GEMM and compact FP8 prefill

This work builds on the preserved
[`dsv41-flash-h100-pd-v9`](https://github.com/CherryLemon/sglang/tree/dsv41-flash-h100-pd-v9)
checkpoint (`27a6e7179db52356b0b44792ff0ccb85db3e951e`). The model, two
8-GPU servers, capacity, PD topology, DSpark and graph settings are the same
as the v9 configuration in [README.md](README.md).

## Implementation

Five H100 FP8 linear shapes now have block32 configurations for small batch
sizes. The existing Triton implementation supports swapping A/B and splitting
K; the configs select these paths without changing scale interpretation or
the GEMM kernel. The selection includes the partial-output reduction cost.
Entries for larger batches retain the original default, including large prefill.

On Hopper prefill with the existing torch candidate selector enabled, the
candidate-source layer stores sorted block IDs instead of a token-wide boolean
mask. Subsequent candidate-consuming layers gather and score only those blocks.
The block selector retains the same padded reduction, forced newest block and
torch TopK. The FP8 score arithmetic retains its BF16 rounding steps. Compact
TopK results are mapped back to logical positions before page-table lookup.
Candidate IDs follow the existing late-layer tail save/slice/restore lifecycle.

At a 600000-token context, each consumer scores at most 16384 candidate positions
per query instead of the full context. A 4096-row candidate table requires
32 MiB of int32 IDs instead of approximately 2.29 GiB of token-mask booleans.
The source layer still scores the full context and the score workspace remains
bounded at 1 GiB. These are storage/work reductions, not endpoint speedup claims.

## Component validation

- 100 GEMM candidates over 20 shapes compared against a dequantized FP32
  reference. Max and RMS error must stay within the unchanged implementation's
  measured error plus a fixed rounding allowance; BF16 outputs are also checked.
- 95 GEMM boundary shapes, including empty inputs and dispatch boundaries,
  with three fixed-address graph replays per shape using changed input/scales.
- 17 compact-prefill context widths from 0 through 600000: reconstructed
  candidate masks, scores and selected score multisets; six graph replays with
  changing visible lengths and candidate IDs; NaN/invalid/tail cases.
- The full score path is bitwise checked against a frozen v9 implementation.
  Compact scores match the gathered dense scores; tied TopK token identities
  are not claimed identical. Compute Sanitizer memcheck reports zero errors.

Results are in [v10-component-results.json](v10-component-results.json).
Runtime hashes are in [v10-manifest.json](v10-manifest.json). The historical
v9 manifest applies to the checkpoint commit, not the modified v10 files.

Reproduce the component checks on an otherwise idle H100 with the pinned
environment described in README.md:

```sh
PYTHONPATH=python python benchmark/deepseek_v41_h100/tune_block32.py \
  --quick --output /tmp/dsv41-tuning.json
PYTHONPATH=python python test/manual/dsv41_h100/check_block32_configs.py \
  --configs python/sglang/kernels/ops/quantization/configs \
  --output /tmp/dsv41-gemm-check.json
PYTHONPATH=python python test/manual/dsv41_h100/check_compact_prefill.py \
  --output /tmp/dsv41-prefill-check.json
compute-sanitizer --tool memcheck --error-exitcode 99 \
  python test/manual/dsv41_h100/check_compact_prefill.py \
  --output /tmp/dsv41-prefill-memcheck.json
```

The initial independent-reference gate was stricter than the unchanged GEMM
could satisfy. The final gate measures control error first; it does not claim
bitwise equivalence across Split-K reduction orders. Component and serving
known-answer tests do not establish full benchmark-suite model quality.

## Endpoint validation

The complete candidate campaign passed: single/16-request functionality,
serial/concurrent mixed-length boundaries, conversations/tools/cancellation,
two coding tasks with 16 known-answer assertions, uneven DP activity (1/3/7/1),
and DSpark verify counters on all four ranks in both serial and parallel tests.
Both servers' runtime hashes and unchanged launch/capacity settings were checked
again after the campaign. Neither server log contained a traceback or ERROR.

Later v11 validation found that this fixed512 workload forces continuation beyond
natural EOS. Treat its throughput as a forced-length stress measurement; see
[V11.md](V11.md) for the correction and a separate natural-EOS coding comparison.

Ten retained warmed repetitions per concurrency use identical input hashes,
approximately 32k input tokens and 512 output tokens per request. No profiling
or standalone component tests overlapped timing. Pooled burst throughput is
all output tokens divided by the sum of all batch wall times:

| Concurrency | Fresh v9 tok/s | v10 tok/s | Change |
|---|---:|---:|---:|
| 1 | 139.6 | 187.6 | +34.3% |
| 4 | 537.5 | 678.1 | +26.2% |
| 16 | 1521.4 | 1721.2 | +13.1% |

Cold first-output-block latency (one exact zero-cache request per arm):

| Input tokens | Fresh v9 seconds | v10 seconds | Reduction |
|---|---:|---:|---:|
| 32768 | 3.137 | 2.840 | 9.5% |
| 131072 | 14.547 | 12.250 | 15.8% |
| 600000 | 117.553 | 80.032 | 31.9% |

All three cold requests retrieved the expected beginning/middle/end values.
Warm TTFT was approximately unchanged; most of the warm gain is in generation.
Full metrics, all repetition rates, hardware samples summarized by role, and
limitations are in [v10-endpoint-results.json](v10-endpoint-results.json).

These are whole-integration measurements, not per-feature attribution or
sustained-arrival SLA capacity. Cold latency has only one sample per length.
The decode Engram huge-page residency varied after restart (baseline 74-100%,
candidate 86-100%); prefill was 100% in both. Five-second hardware samples found
no thermal slowdown or uncorrected volatile ECC during the candidate run.
Monitoring began partway through the baseline. Capacity stayed at 655360 context,
1048576 token pool and max-running 128; the tests do not establish that 16
600k requests can run together.
