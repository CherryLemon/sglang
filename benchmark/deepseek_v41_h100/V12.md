# DeepSeek V4.1 Flash on two 8-H100 nodes: v12

This checkpoint keeps the validated combined implementation for a dedicated
prefill node and a decode node. The accepted workload is cached 131072-token
coding input at 80 concurrent requests, with at least 100 output tokens/s
averaged over the generation phase of every measured request. It is a
workload-specific burst result, not a continuous-arrival or instantaneous
per-token latency guarantee.

The tested runtime is `7a882e727d09ed7b896b44227b80b4e0b0b7481d`.
Subsequent changes in this checkpoint only document configuration and results.
[v12-manifest.json](v12-manifest.json) records the model revision, deployment
bundle, and hashes of all 29 runtime files. The complete model remains loaded
on each node; model precision and the 655360-token context limit are preserved.

## Configuration

Both nodes use eight H100 80GB HBM3 GPUs. Prefill uses TP8/EP8; decode uses
attention TP2 x DP4 and EP8. Both use DSpark block5 with static ragged verify,
the corrected attention-TP reduction, and eight HTTP/tokenizer workers.
Mooncake uses RDMA. The decode prefix cache is disabled.

P uses breakable prefill graphs with query buckets 32/64/128/256, a maximum
aggregate query of 256, and a current-context cap of 131072. Larger queries
or contexts retain eager execution. A cold 131072-token prompt consists of
32 eager 4096-token chunks; a cached prompt with a 256-token tail can use
the graph when the whole batch satisfies its admission rules.

D adds graph buckets 34, 36, and 38 to avoid the previous 32-to-40 padding
cliff. The exact model argv, environment, resource limits, and router settings
are in [v12-launch-config.json](v12-launch-config.json). Replace its model,
host, and RDMA-device placeholders for the deployment; the GID index is
fabric-specific. These are the measured experimental settings, including
the branch's DeepSeek V4.1 PD gate, rather than a claim about an upstream
default recipe. Max-running 384 is an admission setting, not a performance
claim at that concurrency. The P pool does not establish residency for
80 distinct 128k prefixes.

All six requested concurrency levels were reached in scheduler load samples.
Every one of the 394 formal requests completed successfully with natural EOS,
the expected cache count, and zero retractions. The 197 per-concurrency warmup
requests also passed those gates; a separate prefix-warmup request is excluded
from both totals. At concurrency80, the two rounds produced 7049.7 and 7115.8
total output tokens/s, with minimum request generation rates of 103.418 and
103.913 tokens/s. The complete pooled distributions, both round throughputs,
output lengths, and source-result hashes are in
[v12-endpoint-results.json](v12-endpoint-results.json).

Independent generated-code checks passed 579 of 584 distinct programs across
591 burst requests. Five occurrences failed `optimal_schedule` behavioral
checks: one in warmup and four in formal measurements, so formal code checks
passed 390/394. The formal failures occurred at concurrency32 (one), 64 (one),
and80 (two). There were no protocol errors. These failures are preserved;
throughput is not recomputed by dropping semantically incorrect responses.

Telemetry within formal bursts covered 121 P and120 D complete eight-GPU
samples. SM clocks were1830MHz; maximum sampled temperatures were44/53C,
minimum free memory12528/3108MiB for P/D, thermal slowdown flags inactive,
and volatile uncorrected ECC zero. P/D model logs after preflight and1183
router log lines within the burst window had no matching error/retry warnings.
These are sampled observations rather than continuous hardware guarantees.
Both services and the router remained healthy after the sweep. Only the
owned temporary telemetry collectors were stopped.


The same pre-tokenized six-API Python coding request is sent through the
normal PD router's native `/generate` endpoint. Each request has 131072 input
tokens and reports 130816 cached P tokens, leaving 256 new query tokens.
D retains independent KV per request. Temperature is zero, EOS is honored,
and the output budget is 8192. A prefix warmup and one burst per concurrency
are excluded; the next two bursts are measured. No profiler is attached.

Total output throughput is completed output tokens divided by the sum of
measured burst wall times, including admission, prefill, transfer, and drain.
Per-request generation speed is `(output_tokens - 1) / (last_content_time -
first_content_time)`. TTFT is the arrival of the first generated stream chunk;
TPOT is the corresponding generation-interval estimate. Native token IDs
exclude chat rendering and BPE work. Quantiles pool individual requests,
not round quantiles, and code semantics are checked separately from API/EOS
success. Two bursts at concurrency one provide only two measured requests.

## Additional validation and limits

The earlier candidate5 combined run completed 624 API/cache/natural-EOS
requests with explicit zero retractions, including warmup. The two formal
80-request bursts had minimum generation rates of 103.004 and 102.816
tokens/s. The two formal 128-request bursts reached real running128 but had
minimum rates of 76.104 and 75.240; they do not satisfy the 100 tokens/s goal.
The independent generated-code checker passed 618 of 624 distinct programs;
six had RollbackDSU semantic errors, with zero protocol errors. API success
must not be described as universal generated-program correctness.

Seven known-answer boundary requests passed, including cold 600000 tokens
and subsequent reuse of the cached 131072-token graph. All eight P ranks
completed capture. The latest cold boundary records are nonstreaming
correctness measurements, not a new cold-TTFT benchmark. Historical v11
cold/warm performance is retained in its original report.

A separate direct-PD diagnostic completed 128 requests at the controlled
distribution 32/33/31/32 with zero generation errors or retractions; all
128 generated programs passed the checker. Capture logs, target graph logs,
and the verified replay-selection source jointly support target graph34
at that distribution. This was not an Nsight measurement or a normal-router
performance result. Three later load-monitor requests disconnected; these
were recorded and did not affect generation. The earlier legal router retry
and slow round remain documented in [V12_INTEGRATED.md](V12_INTEGRATED.md).

P has no newly established independent throughput or distinct-prefix
capacity limit. Its high-concurrency cached batches usually contain more
than 256 aggregate query tokens and therefore execute eagerly. End-to-end
TTFT includes frontend, scheduling, P compute, transfer, and D's first step;
it cannot be attributed entirely to P GPU time.

## Investigations retained outside the runtime

A TileLang indexer research implementation passed its frozen numerical and
graph gates after reproducing the reference reduction order. Its eight
qualified component measurements were 39.9%-135.8% slower than the accepted
Triton group6 path, so it was not integrated. This compares implementations,
not language-level theoretical ceilings. The accepted mHC path uses
TileLang.

Real-route MoE tactic changes were not integrated because the promising
case-specific tactic regressed uniform routing. See
[V12_MOE_INVESTIGATION.md](V12_MOE_INVESTIGATION.md). Expert-placement and
padding-mask work remains source/design research; there is no static expert
remap, replica, online EPLB, or padding patch in this checkpoint. A proposed
new candidate5 Nsight run was prepared but never started. The preserved
earlier all-rank traces describe their own pinned baseline, not this final
runtime.
